# NurByte — task to merge

1. Receive the task and assigned repository/environment. Create a task branch from dev for features/fixes, or master for an explicitly assigned production hotfix. Preserve existing edits. Do not enter the other environment.
2. Present a short solution plan (alternatives only when useful), target version, checks and deployment effects. Wait for the user's plan/solution approval before implementation. Creating the task branch and read-only analysis are allowed before plan approval.
3. Implement the approved plan, commit only scoped changes and run risk-appropriate checks. Do not ask routine questions about commit titles, branch names or individual commands. Report blockers honestly.
4. Present the result and ONE final decision: accept changes and merge to the assigned target, or request corrections. Show repository, source/target, exact full commit SHA(s), version, checks and automatic deployment effects. The final acceptance explicitly covers the necessary push, PR creation, CI verification, merge, switching/safely synchronizing the target and deleting the task branch locally and remotely. Do not demand an already-existing PR number before approval when the approved process creates it.
5. After acceptance execute the whole announced process without new conversational approvals: push the exact approved commit, verify remote SHA, create/find the PR, inspect required checks, merge the approved head, switch/synchronize the target, delete source locally/remotely, report completion. If only publication/Preview is needed before final review, ask once for that push+PR scope; do not repeat it later for unchanged commits. Approval of the solution PLAN alone never authorizes push or merge.
6. Branch deletion after a confirmed successful merge is standing user policy for ALL task types (feat/fix/hotfix); do not ask for deletion consent separately or routinely offer a keep-branch choice. Still preserve new/unmerged work: stop unsafe cleanup on dirty checkout, occupied worktree, changed source SHA or failed/ambiguous merge. Never force-delete, reset, clean, stash or bypass checks to finish. Verify server merge first and protect remote deletion against new commits.
7. No new question unless the commits, target, scope or deployment effects change, checks reveal a blocker, or the user requests a revision. Inspect state before retrying an uncertain result. Respect mandatory runtime/tool security prompts; never fabricate approval, disable guards or promise zero security prompts. Use `push.py --approved-sha FULL_SHA` after valid final consent; do not trigger its TTY confirmation again.
8. DEV beta builds: X.Y.Z-beta.1, beta.2, etc. For a feature-complete planned release use X.Y.Z-rc.1, rc.2; stable is X.Y.Z. Never mechanically convert every existing version during configuration maintenance. Prepare bumps before checks/final approval. GitHub Release/tags/artifacts/migrations/production feeds need explicit inclusion in the approved scope. A master merge's disclosed automatic production deployment is covered by that final approval.

Status updates only at meaningful transitions: 🔵 planning/implementation/checks, 🟡 waiting for user or CI, 🔴 blocked/error, 🟢 completed. State what is running or what is blocking. Do not claim a process is hung solely because output is quiet. Finish with merge result, active branch, source deletion local/remote and any blocker. Routine Git needs no subagents, web research, full policy reread or repeat of valid checks for an unchanged SHA. This policy does not change remote permissions or security controls.

## Execution
Use finish.py with a reviewed JSON plan and --approved-plan DIGEST after final user consent. Read FINISH.md only for first use or an exception. It uses merge commits (no squash/rebase), checks SHA/base, resumes existing PRs and stops on dirty worktrees or failed/pending CI. It never bypasses protected branches. For pending CI resume the same unchanged approved plan; no repeated consent. No automatic API token/model call is involved.

## Progress contract
Before implementation show the plan including verification, wait for approval, track done/current/next and update it for newly discovered required work. Final reports must include remaining work and the next action, not just failures. Run approved scoped checks without redundant questions. Detailed blocked-task reporting: COMPLETION.md.
